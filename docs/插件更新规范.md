# 插件更新规范

这份文档说两件事：**用户怎么更新插件**，以及**插件作者怎么发新版**。

---

## 一、用户侧：更新已安装的插件

### 在哪看有没有新版

面板「插件」页顶部会出现提示条：

```
3 个插件有新版本，去「插件市场」一键更新。  全部更新
```

没有提示条说明全部是最新的。检测是自动的（启动后 30 秒一次，之后每小时一次），
结果缓存 5 分钟；点「插件市场」里的「重新获取」会强制重查。

### 单个更新

「插件市场」里，有新版 的插件会显示版本箭头和更新按钮：

```
回声 v1.1.0   [可更新 1.0.0 → 1.1.0]
                          [更新到 1.1.0]
```

点「更新」会先弹窗确认——**插件目录会被整体覆盖**，你手动改过的代码会丢。
玩家存档在 `data/bots/<机器人id>/plugins/<id>/` 下，不受影响。

### 批量更新

点提示条里的「全部更新」，会列出所有待更新插件及版本变化，确认后一次性处理。

```
以下插件会被覆盖更新：

dice 1.0.0→1.1.0
echo 0.9.0→1.1.0
```

结束后报告成功 / 跳过 / 失败数量。**单个插件失败不影响其他插件**，
失败的那个保持原版本不动。

### 更新过程中发生了什么

```
1. git clone --depth 1 插件仓库到临时目录     ← 只 clone 一次，不管更新几个
2. 逐个插件：现有目录改名成备份 → 复制新版进来
3. 复制失败 → 把备份改回去，该插件保持旧版本
4. 全部成功后删除临时目录（连同备份）
5. 重载更新过的插件
```

所以更新是**要么成功、要么原样不动**，不会出现「更到一半」的中间状态。

### 自动更新

默认**关闭**。要开启得手改配置（暂时没有面板开关）：

```jsonc
// config/bot.json（全局）
"plugins": { "autoUpdate": true }
```

开启后每次启动自动更新所有有新版 的插件。默认关闭是有意的：
自动更新会覆盖 `plugins/` 里的目录，用户自己改过的代码会静默丢失。

## 二、插件作者侧：怎么发新版

### 1. 版本号写在哪

**内建插件**（`index.js`）——写在默认导出的 `version` 字段：

```js
export default {
  id: 'echo',
  name: '回声',
  version: '1.1.0',        // ← 改这里
  description: '...',
  setup(ctx) { /* ... */ },
};
```

**外部插件**（`plugin.json`）——写在 `version` 字段：

```json
{ "id": "kun-py", "name": "养鲲（Python）", "version": "2.0.0" }
```

> 框架读版本号时，内建插件会 `import` 模块取默认导出（不执行 `setup`），
> 外部插件直接读 `plugin.json`。两边读不到就不提示更新，不会报错。

### 2. 两处版本号必须一致

| 位置 | 作用 |
|------|------|
| 插件代码里的 `version` | **框架检测更新看的是这个** |
| `index.json` 里的 `version` | 面板市场列表显示用 |

只改一处会出现「市场显示 v2.0.0 但不提示更新」或反过来。
发布前核对一遍。

### 3. 版本号格式

用语义化版本 `主.次.修订`，可带预发行标签：

```
1.0.0        ← 正式版
1.0.0-beta   ← 预发行，比 1.0.0 旧
2.0.0        ← 破坏性变更
```

比较规则：

- `2.0.0 > 1.9.9`（主版本优先）
- `1.0.0 > 1.0.0-beta`（预发行低于正式版）
- 解析不了的版本号（比如写了 `v1.0` 或 `next`）当作**相等**，不提示更新

### 4. 什么时候升哪个号

| 变更类型 | 升 | 例子 |
|----------|-----|------|
| 破坏性变更：改了存档结构、删了命令、改了配置项含义 | **主** | 1.9.0 → 2.0.0 |
| 新功能、新命令，向后兼容 | **次** | 1.1.0 → 1.2.0 |
| 修 bug、改文案 | **修订** | 1.1.0 → 1.1.1 |

**破坏性变更一定要升主版本号**——用户的存档在 `data/` 下，
更新插件不会动存档。如果你的新版本读不懂旧存档，必须升主版本，
让用户知道要手动处理。

### 5. 存档兼容性

插件的存档目录是 `data/bots/<机器人id>/plugins/<id>/`，
**更新插件不会碰它**。所以：

- 存档结构变了吗？变了就升主版本，并在更新说明里写清楚
- 新版本能读旧存档吗？不能的话，考虑在 `setup()` 里做一次迁移
- `ctx.storage` 的键名别随便改，改了旧数据就orphan了

### 6. 提交到插件仓库

```bash
# 1. 改插件代码里的 version（要写成字面量，别用常量）
# 2. 重算索引（版本号、sha256 都由脚本算，不要手改）
node scripts/build-index.mjs
# 3. 提交
git add plugins/你的插件/ index.json
git commit -m "feat(你的插件): 1.2.0 加了什么"
git push
```

**`index.json` 不要手改**：里面的 `sha256` 是插件目录的内容指纹，
手写的一定对不上，用户安装时会校验失败。跑脚本就行。
`node scripts/build-index.mjs --check` 可以提前查（CI 跑的就是这个）。

用户端最长 5 分钟内就能看到新版（检测有缓存）。

## 三、已知限制

- **备份在系统临时目录**，不在 `plugins/` 旁边。放在旁边会被 loader 扫成
  `xxx.bak-1699` 这样的幽灵插件。
- **更新前不比对内容**，只看版本号。版本号没变但文件变了，不会更新。
- **`plugins/` 里的本地修改一定丢**。想保留自己改的版本，就别用市场更新，
  或者先把插件目录复制出来。
- **自动更新只在内建/外部插件目录层面生效**，不动 `config/bots/<id>/plugins/`
  下的用户配置——你在面板里调过的参数不会被动。
