# AI 宿主插件方案（ai-chat v3）

> 目标：把现在那份 710 行的 `ai-chat` 重写成一个**能接各种 AI 工作台**的插件。
> DSH 只是其中一个分支，以后还能接 Claude Code、Cursor、本地 Ollama、自建服务。

---

## 一、三条约束，先对一遍

| 约束 | 结论 |
|---|---|
| 要**按群开关**，能自由选哪些群开 | → 必须做成 **Roost 插件**（内核通道做不到，见第三节） |
| 要能接**大部分 AI 工作台** | → 核心抽象是 **Adapter**，宿主换适配器不换插件 |
| DSH 只是**一个分支** | → 插件定义「宿主协议」，DSH 是协议的一个实现 |

三条合起来只有一个解：**插件 + 适配器 + 一份宿主协议**。

---

## 二、现在的 ai-chat 是什么

710 行，OpenAI 兼容，能跑但停在「单轮问答」：

| 已有 | 说明 |
|---|---|
| 每会话独立上下文 | `chatId → history`，闲置回收 |
| OpenAI 兼容 | 改 `baseUrl` 就能换 DeepSeek / Kimi / 通义 / Ollama |
| 内置命令 | `/ai`、`/新会话`、`/清空`、`/重置`、`/模型`、`/停止` |
| 访问控制 | `open` / `allowlist` |
| 面板配置 | 密钥、模型、提示词、温度、超时、markdown |

**缺的**（也就是「简陋」的地方）：

- **只能直连模型**：接不了 DSH / Claude / Cursor 这类有工具、有记忆、有 agent loop 的工作台
- **只认纯文本**：语音的官方 ASR、图片、引用、合并转发、卡片全都没用上
- **没有工具调用**：模型不能查群、不能发图、不能调官方接口
- **没有记忆**：只有一段滑动的对话历史
- **没有流式**：长回答只能等

---

## 三、为什么必须是插件，不是内核

上一版我把通道做进了内核（v0.8.0）。那是**给外部工具用的旁路**，不是主路径。原因：

| | 内核通道（v0.8.0） | 插件（本方案） |
|---|---|---|
| 按群开关 | ❌ 绕过分群开关，全量推 | ✅ `pluginAllowedIn` 在监听器层就拦 |
| 谁在用 | 管理员级外部程序 | 普通用户在面板里开关 |
| 卸载 | 得改配置/重启 | 面板一点 |
| 权限 | 持 accessKey = 管理员 | 插件级权限 |

**内核通道保留**，作为「不想装插件、只想用脚本接一下」的旁路，文档里写明它是管理员级、不受分群开关约束。

## 四、架构

```
QQ 官方
  ↓  WebSocket / Webhook
┌──────────────────────────────────────────────┐
│ Roost 内核                                     │
│  网关 / 凭证 / 限频 / 被动窗口 / 消息规范化      │
│  47 个官方接口                                 │
└──────────────────────────────────────────────┘
  ↓ ctx.on('message')     ↑ msg.reply() / ctx.push()
┌──────────────────────────────────────────────┐
│ ai-chat 插件（按群开关）                        │
│  · 群策略：哪些群开、理不理没 @ 的、谁优先       │
│  · 会话：chatId → 上下文 / 宿主会话 id          │
│  · 入站整形：语音 ASR、引用、合并转发 → 文本     │
│  · 出站整形：分段、引用、@、限流、markdown       │
│  · 记忆：ctx.storage                          │
└──────────────────────────────────────────────┘
  ↓ 宿主协议（HTTP）      ↑ 回话
┌──────────────────────────────────────────────┐
│ Adapter（选一个）                              │
│  ├ openai   直连 OpenAI 兼容端点（默认）        │
│  ├ dsh      推给 DSH 插件，用它的 agent loop    │
│  ├ webhook  推给任意 HTTP 服务                 │
│  └ mcp      反向：把 QQ 能力暴露给工作台         │
└──────────────────────────────────────────────┘
```

## 五、宿主协议（这是本方案的核心产出）

插件和宿主之间只认这一份协议。**写一个新分支 = 实现这两端**，插件本体不动。

### ① 插件 → 宿主：推一条消息

```jsonc
POST <host.url>/inbound
{
  "id": "evt_01H...",                  // 本次事件 id，回话时带上
  "bot": "main",
  "chat": {
    "kind": "group",                   // group | c2c
    "chatId": "B2C3...",
    "name": "测试群",
    "groupId": "B2C3..."
  },
  "sender": { "id": "A1B2...", "name": "小明", "role": "member" },
  "text": "看图",                       // 已去掉 @机器人 前缀
  "quoted": "上一句被引用的话",          // 没有就是空串
  "attachments": [
    { "type": "voice", "asrText": "你好", "wavUrl": "https://...wav" },
    { "type": "image", "url": "https://..." }
  ],
  "elements": [ { "type": "chatRecord", "content": "..." } ],
  "history": [                          // 插件侧维护的最近若干轮，宿主可以不存
    { "role": "user", "content": "..." },
    { "role": "assistant", "content": "..." }
  ],
  "reply": {
    "url": "http://127.0.0.1:8080/api/plugins/ai-chat/r/reply",
    "token": "一次性回话令牌",
    "expiresAt": 1761456300000
  }
}
```

### ② 宿主 → 插件：回话

```jsonc
POST /api/plugins/ai-chat/r/reply
{
  "id": "evt_01H...",
  "token": "一次性回话令牌",
  "text": "看到了，是只猫。",
  "markdown": false,                   // true 就用官方 markdown 消息
  "replyTo": "msgId",                  // 可选：引用/被动回复哪条
  "done": true                         // false 表示「还有后续」，插件会等
}
```

**设计要点**

- **一次性令牌**：`reply.token` 只对本次事件有效，防止外部猜 URL 往群里发消息
- **`done:false` 支持分段**：宿主可以先发一句「我想想」，再发正文
- **超时兜底**：`expiresAt` 之后插件丢弃，不会无限等
- **不传 `history` 也行**：宿主自己存上下文的话，忽略 `history` 即可

## 六、四种 Adapter

| Adapter | 接谁 | 需要额外装什么 | 能用到什么 |
|---|---|---|---|
| **`openai`**（默认） | DeepSeek / Kimi / 通义 / 智谱 / 硅基流动 / 火山 / **Ollama / vLLM / LM Studio / one-api** | 什么都不用 | 纯对话 |
| **`dsh`** | DeepSeek Harness | 装 `dsh-roost` | agent loop、工具、记忆、压缩 |
| **`webhook`** | 任何能收 HTTP 的自建服务 | 无 | 自己实现 |
| **`mcp`** | Claude Desktop / Cursor / Cline / Continue / Windsurf / DSH | 加一行配置 | **反向**：工作台当手脚 |

### `openai` 覆盖多少

OpenAI 兼容的 `/chat/completions` 已经是事实标准。**这一个适配器就覆盖了「大部分 AI 工作台」**——
只要它肯暴露一个 OpenAI 兼容端点，或者你中间加个 one-api / LiteLLM 做协议转换。

### `mcp` 是另一个方向

前三个是「工作台当大脑」：QQ 消息进来，工作台想，插件发出去。
`mcp` 是反的：**工作台当手脚**，在 Claude/Cursor 里说「帮我在群里发一句」，它调插件。

插件侧暴露 REST，另配一个几十行的 stdio 桥：

```jsonc
// claude_desktop_config.json
{ "mcpServers": { "qq": {
    "command": "npx", "args": ["-y", "roost-mcp"],
    "env": { "ROOST_URL": "http://127.0.0.1:8080", "ROOST_KEY": "..." }
} } }
```

工具集：`qq_send` / `qq_recall` / `qq_mute` / `qq_group_info` / `qq_api`。
**任何支持 MCP 的工作台，加一行配置就能调 QQ。**

## 七、和现有 ai-chat 的关系

**不换 id、不换配置键**，直接升到 `3.0.0`：

- 用户已有的 `apiKey` / `baseUrl` / `model` / 提示词全部继续有效
- 新增 `adapter` 字段（默认 `openai`），默认值就是现在的行为，**升级后什么都不用改**
- 想换 DSH 就把 `adapter` 改成 `dsh`、填 DSH 的地址

保留的：每会话上下文、闲置回收、内置命令、访问控制、面板配置。
砍掉的：无。**只加不减**，避免升级踩坑。

新增：
- `adapter` 选择 + 各适配器自己的配置块
- 入站整形（ASR / 引用 / 合并转发 / 图片）
- 出站整形（分段、引用回复、markdown、长文截断）
- 记忆（`ctx.storage`，可选开关）
- `/人格` 命令，按群切人格

## 八、目录结构

```
plugins/ai-chat/
  index.js              插件入口：命令、配置、群策略、出站整形
  adapter/
    index.js            适配器注册与选择
    openai.js           直连 OpenAI 兼容端点（现在的能力搬过来）
    dsh.js              推给 dsh-roost
    webhook.js          通用 HTTP
  inbound.js            消息整形：语音/引用/合并转发 → 给宿主的文本
  outbound.js           回话整形：分段/引用/限流/长文
  session.js            会话与记忆
  README.md
```

MCP 桥单独一个包（`roost-mcp`），因为它要被 `npx` 装到工作台那边，不能塞在插件里。

## 十、已拍板的三个决定

| 问题 | 决定 |
|---|---|
| 插件 id | **保留 `ai-chat`**，最终升到 `3.0.0`。配置键不变，老用户不用重填密钥 |
| 默认适配器 | **`openai`，预填 DeepSeek**。装上填个密钥就能用，跟现在体验一致 |
| MCP 桥 | **放到 M5**，先把主链路跑通 |

### 版本节奏

- `1.3.0`（M1）：加适配器接缝 + `adapter` 配置项，**行为不变**
- `2.0.0`（M2~M3）：入站/出站整形、`webhook` 适配器——宿主协议成型
- `3.0.0`（M4~M6）：`dsh` 适配器、MCP 桥、记忆与按群人格

## 附：为什么不做「一个插件塞所有宿主」

每个宿主的认证、会话、工具协议都不一样。硬塞进一个文件的结果就是
`if (host === 'dsh') ... else if (host === 'claude') ...` 长成 3000 行。

适配器模式的价值不在「代码好看」，在于：**加一个新宿主只动一个文件，
而且不会碰已经在跑的旧分支。**
